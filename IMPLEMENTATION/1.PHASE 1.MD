## Phase 1 – MVP (Game Mode / Factory Puzzles)

Phase 1 delivers the core game mode with self-contained Spark puzzles in the distributed factory setting. The focus here is to build a Minimum Viable Product that is playable and educational, so that users can start solving visual Spark problems and get immediate feedback. This phase will include a set of short, focused puzzles, an interactive code editor, animated visualizations for each puzzle, and a judging system that checks solutions. Below we detail the Phase 1 design:
Core Gameplay Loop & User Experience
•	Puzzle Selection: The user starts by selecting a puzzle from a list or map of puzzles. Puzzles are labeled by difficulty (easy, medium, hard) and tagged by concept (e.g. join, shuffle, aggregation). For example, a beginner might choose an easy puzzle tagged “GroupBy” or “Join”.
•	Puzzle Presentation: Once a puzzle is chosen, the screen splits into two main parts. On one side, the Factory View illustrates the initial state of the factory for that puzzle: e.g. multiple conveyor belts with input data (depicted as colored boxes or items with labels) and some machines or tubes showing how data should flow. There is also a text description of the problem scenario, which explains in plain language what needs to happen (e.g. “Combine the products by category” or “Attach the supplier info to each product using a join”). The goal (expected outcome) may be described textually and possibly visualized as the target arrangement of boxes on an output conveyor.
•	Coding Interface: On the other side (or bottom, depending on layout) is a code editor where the user writes a short PySpark snippet (Phase 1 will focus on PySpark for simplicity). This editor will likely use the Monaco Editor (which powers VS Code) for a rich in-browser coding experience[3]. Basic syntax highlighting, auto-completion for PySpark commands, and perhaps templates or placeholders for novices will be provided. The user might either start from scratch or be given a partial code with blanks to fill in, depending on puzzle type.
•	Running the Code (Executing the Factory): The user clicks a “Run the Factory” or “Start Factory” button. The backend takes the code, executes it on the puzzle’s input data (or simulates execution), and meanwhile the UI plays an animation in the Factory View:
•	Conveyors move their boxes into machines as the code’s transformations are applied.
•	If the user’s code performs a map or filter, we see boxes getting changed or some boxes being removed by a “filter machine”.
•	If there’s a shuffle operation (like a groupByKey, join without broadcast, or repartition), the animation will show items entering teleport tubes or pipes, mixing and coming out redistributed on different conveyors (simulating data moving across partitions/nodes).
•	If the code triggers an expensive or wrong operation, the animation might dramatize it (e.g. machines shaking or a backlog of boxes forming to indicate a bottleneck or skew).
•	The animation ends with the final output: e.g. boxes on an output conveyor, which can be visually compared to the expected outcome. Success might be shown with celebratory effects (green lights, confetti from machines), whereas incorrect output might show a red light or an alarm.
•	Run Report & Feedback: After the animation, a Run Report panel pops up (the Judge View results). This report includes:
•	Output Correctness: A checkmark ✅ if the output matches the expected results, or an ❌ with an explanation if not. If incorrect, it may show a small diff or message like “The output items don’t match the expected result.”
•	Performance Metrics: Key metrics from the execution:
o	Time/Speed: For MVP this can be a simulated value (e.g. based on number of operations). It might say “⏱️ Time: 1.2s – Good” for a fast solution or “⏱️ Time: 5.3s – Could be faster”. In reality, Spark jobs are measured in seconds or minutes, but for game simplicity these will be small numbers, possibly scaled.
o	Shuffles: “🔁 Shuffles: N” indicating how many shuffle operations occurred. Ideally 0 or 1 for simple puzzles. It might label it as Low/Medium/High. For example, using a broadcast join would result in 0 shuffle in that join step (not counting upstream operations), which the report could mark as Low (good). A normal join or multiple wide operations might say High and be flagged.
o	Stages: “🏭 Stages: X” – number of Spark stages the job was broken into (Spark pipeline DAG depth). Simpler code yields fewer stages. This teaches users that more complex or ill-planned jobs cause extra stages.
o	Resource Usage: e.g. “📦 Max Partition Skew: Y items” – indicating the largest partition size. If one partition had far more data than others (skew), the report might highlight it (“Skewed: one partition has 5× more data than average!” vs “Balanced”). Similarly, memory usage or a note if the user cached data could appear (Phase 1 might simplify this).
•	Star Rating: Based on the above metrics, the solution is given a rating (for example, 3 stars if it’s correct and meets efficiency goals, 2 stars if correct but not optimal, 1 star if it barely works or is very inefficient). This gamifies the optimization aspect – users are encouraged to improve their code to get more stars.
•	Hint: If the user didn’t achieve the optimal solution, a hint message is provided. Hints are short suggestions keyed to what the user’s code did. For example: “Hint: You joined a large and small dataset without a broadcast – try using broadcast() on the small one to avoid a costly shuffle.” or “Hint: Filtering after the join caused unnecessary data processing – filter earlier next time.” These hints either come from simple pattern detection in the code (e.g. a rule that checks for join usage and data size hints) or from an AI assistant that analyzes the run. The hint system in Phase 1 will be fairly minimal and pattern-based.
This core loop ensures the user is engaged with a visual outcome for their code and learns by iterating. They can modify their code based on the feedback and run again until they solve the puzzle with a satisfactory result. The UX emphasizes quick iteration: small puzzles with fast feedback cycles, enticing visuals, and clear indicators of what to improve.
Puzzle Types & Variety in Phase 1
To keep the game interesting, Phase 1 will feature a variety of puzzle types, each highlighting different Spark concepts within the factory metaphor:
•	Rearrangement Puzzles: Focus on partitioning and grouping. The task might be to rearrange or group data in a certain way. For example, given items scattered across conveyors, use a Spark transformation to group similar items together. This teaches operations like groupByKey, orderBy, or repartition to control data distribution. Factory metaphor: The user might need to route boxes into bins by color or label, simulating a group-by operation.
•	Join Puzzles: In these, two (or more) streams of items must be merged correctly. The classic scenario is joining a big dataset with a small one. The puzzle goal could be to attach properties from one set of items to another (like enriching products with category info). This introduces join operations and the concept of broadcast vs shuffle join. Factory metaphor: Two conveyor belts converge into a machine that merges items; using a “broadcast” might be depicted as the small set being replicated at each machine worker to avoid using the teleport tubes (shuffle).
•	Aggregation Puzzles: These involve computing summaries (e.g. counts, sums) per group. The goal might be to produce an output that counts how many items of each type appear, etc. Spark actions like reduceByKey or DataFrame aggregations are in play. Factory metaphor: Boxes with numbers might go into a machine that totals them by category, with a dial showing the sum, resulting in one output box per category containing the aggregate result.
•	Filter/Order Puzzles: Simple but important tasks like filtering out defective items or sorting items. These puzzles highlight transformation order – e.g. doing a filter before an expensive operation. Metaphor: A filter is a machine that lets certain boxes pass (others get discarded into a bin). Sorting might be shown as a conveyor that reorders items.
•	Debug/Fix-it Puzzles: The user is given a tiny Spark snippet that has a mistake or inefficiency and a resulting faulty factory state. For example, the code might produce the wrong output or run too slowly. The user’s job is to edit the code to fix the bug or optimize it. This puzzle type teaches reading and understanding Spark code. Metaphor: The factory might be jammed or producing the wrong goods, and the user must tweak the machine settings (code) to fix it.
•	“Toy Streaming” Puzzles (optional in Phase 1): If included, these would simulate a simplified streaming scenario (data arriving continuously) where the user has to update an aggregation or join on the fly. However, streaming might be advanced, so Phase 1 will likely stick to batch-oriented puzzles.
Each puzzle type ensures that users encounter different Spark challenges in a controlled, small-scale environment. The emphasis in Phase 1 is on small, well-defined problems that can be solved with a few lines of Spark code (one or two transformations), making it feasible to run them quickly and visualize them easily.
User Personas for Phase 1
To tailor the experience and content, we define a few key user personas who would benefit from this product and describe how Phase 1 serves them:
•	Persona 1: “The Junior Data Engineer” – Alice: Alice is a new data engineer with basic Python/Pandas knowledge but new to Spark’s distributed concepts. She finds Spark intimidating. Using this game, she can learn by doing in a sandbox. The visual feedback helps Alice intuitively grasp what a “shuffle” or “partition” means (seeing boxes flying through tubes). Phase 1 puzzles start easy, giving Alice confidence as she sees her code make the factory work. Alice appreciates the hints when she writes non-optimal code, as it teaches her best practices (like broadcasting small tables to avoid shuffles).
•	Persona 2: “The Interview Prepper” – Bob: Bob is preparing for data engineer interviews, where Spark knowledge is tested. He knows theory but wants practice with optimization problems. Bob uses the puzzle mode to cement concepts (e.g. he’s heard of skew issues and broadcast joins, but the game lets him actually apply them). The LeetCode-style judging and star system give Bob a way to measure if his solutions are not just correct but optimal – critical for interview scenarios. Phase 1 provides bite-sized challenges that mirror what might be trivia or sub-problems in interviews.
•	Persona 3: “The Data Scientist (Spark Newbie)” – Carol: Carol is a data scientist who typically works with Pandas and SQL. Her company is transitioning to Spark for bigger data. She uses the game for a gentle introduction. The factory theme makes learning fun (a break from dry documentation). Carol might not care for stars, but she values that the game points out performance pitfalls (because as a beginner she might write something that works on small data but would fail on big data – the game’s feedback teaches her to avoid that early).
•	Persona 4: “The Seasoned Spark Developer (for fun)” – Dev: Dev is already proficient in Spark. He’s curious about this game as a novelty and possibly to recommend to juniors on his team. Dev might zoom through early puzzles, but the harder ones (especially those marked hard with tricky performance issues) challenge his knowledge. He enjoys competing for 3-star solutions and perhaps the leaderboard if one exists. For him, Phase 1 is a refreshing way to validate his expertise and maybe discover new tricks (if puzzles incorporate uncommon scenarios).
•	Persona 5: “The Educator” – Erin: Erin is a teacher or mentor who wants an interactive tool for her students to learn Spark. She uses the game in a classroom or workshop setting. Phase 1 puzzles give her a structured set of examples to demonstrate concepts. She might assign some puzzles as homework. The instant feedback means students can learn independently. Erin likes that the puzzles are tagged by concept, so she can align them with her curriculum (e.g. have students do all the “join” related puzzles after a lecture on joins).
These personas illustrate the range of users: from beginners to experienced practitioners, and even educators. Phase 1 is primarily aimed at beginners and intermediate users (like Alice, Bob, Carol), but with enough depth (via optional hard puzzles) to engage advanced users (like Dev) as well. The gamified approach lowers the entry barrier for learning Spark, while the LeetCode-style evaluation satisfies those who crave measurable progress or are goal-oriented.
Example Puzzles (5 Sample Puzzles for Phase 1)
To concretize the MVP, here are five sample puzzles with details on their setup, Spark concepts, solutions, animation, and judging. Each example shows how the factory theme and Spark problem come together:
Puzzle 1: “Group the Fruits” (Rearrangement Puzzle, Easy)
- Scenario & Visual Setup: The factory has three conveyor belts as input, each carrying a mix of fruit items (say apples, bananas, cherries represented as red, yellow, and purple boxes with icons). The fruits are randomly distributed across the belts. At the end, there are three bins or output conveyors labeled “Apples”, “Bananas”, “Cherries”. Currently, the fruits are all mixed up. The goal is to group the same fruits together into their respective bins.
- Spark Concept: Partitioning and grouping by key. The user needs to transform the dataset so that items are grouped by fruit type. This can be done with something like a .groupByKey() or using DataFrame groupBy, or even sorting by key. It’s conceptually a shuffle operation because data has to be reorganized from random distribution into groups.
- Task for User: Write a Spark snippet that takes an RDD or DataFrame of fruits (with a key like fruit type) and outputs grouped data (e.g. a DataFrame where all apples come first, then bananas, etc., or perhaps a groupBy that results in (fruit_type, [list of items]) structure). In PySpark, one approach could be: grouped = fruitsRDD.groupBy(lambda fruit: fruit.type) followed by collecting or mapping to output, or if using DataFrame: fruitsDF.groupBy("type").agg(collect_list("item")) just conceptually. But since this is a small puzzle, even a sort by type could achieve grouping in output.
- Correct Solution Sketch: A minimal solution might be:
grouped = fruitsDF.orderBy("fruit_type") 
# or fruitsRDD.sortBy(lambda fruit: fruit.type)
grouped.show()  # implicit in the puzzle to produce output
This ensures all apples, then bananas, then cherries are together. Another solution:
result = fruitsRDD.groupBy(lambda fruit: fruit.type).collect()
and then format that into bins. The key is any solution that causes the fruits to be batched by type.
- Factory Animation: When the user runs their code, the animation shows the three input belts feeding into a central sorting machine. The machine identifies each fruit and sends it out through teleport tubes to the correct output bin’s conveyor. Apples go one way, bananas another, etc. We see tubes light up in three colors corresponding to fruit types. If the user’s code correctly grouped them, by the end of the run all apples boxes end up in the “Apples” bin, etc. If they used a groupBy (shuffle), we explicitly show the shuffle: items from all three belts mixing and then separating into groups. If they attempted something incorrect (like not actually grouping), the output conveyors will show a wrong mix (and the correctness check will fail).
- Judge Feedback: This puzzle expects a shuffle (it’s inevitable to group globally). The correctness check ensures each bin has only one fruit type. Performance-wise, any grouping will involve a shuffle, so the report might always show “Shuffles: 1 (expected for grouping task)”. If the user did something suboptimal like collect all data to the driver and then group in Python, the system might detect that (though in Phase 1, we may not consider that scenario). A correct and reasonably efficient solution gets 3 stars (since there’s not much optimization alternative here except doing it). The hint if failed might be generic like “Hint: Try using a groupBy or sort to gather similar items together.”
Puzzle 2: “Fast Join – Enrich Orders with Cities” (Join Puzzle, Medium)
- Scenario & Visual Setup: There are two input conveyor belts in the factory: - The first belt has Order boxes (imagine each box has an order ID and a city code where it was made). - The second belt has City Info boxes (each contains a city code and the full city name, population, etc.). The City Info belt is much shorter (small dataset) compared to the Orders belt which has many more boxes. The goal is to have a machine that merges each Order with its corresponding City info – effectively adding the city name to each order. Visually, there’s a merging machine where belt A (orders) and belt B (city info) feed in, and the output conveyor from the machine should have enriched Order boxes (e.g. an order box that now also shows the city name on it).
- Spark Concept: Joining a large dataset with a small dataset. The key concept to teach is the broadcast join to avoid an expensive shuffle[1]. By default, a join on city code will shuffle both orders and cities by city code. But since City Info is small (dimension table), it’s ideal to broadcast it.
- Task for User: Write a Spark DataFrame join (or RDD join) between the orders and cities on the city code. Ensure it’s efficient. In PySpark DataFrame API, for example:
enriched = ordersDF.join(broadcast(citiesDF), ordersDF.city_code == citiesDF.city_code)
(with an import of from pyspark.sql.functions import broadcast). Without broadcast, a normal join would still produce correct output but be slower (and for our metrics, produce a “shuffle”).
- Correct Solution Sketch: The optimal solution uses Spark’s broadcast. If using RDD:
citiesDict = {c.code: c.name for c in cities}  # collect small dataset to driver
enrichedRDD = ordersRDD.map(lambda o: (o.id, o.city_code, citiesDict[o.city_code], ...))
(This is one way: send small data to all nodes by driver collection – which is effectively a broadcast in logic). Or using DataFrames as shown with broadcast(). A non-optimal but working solution would be:
enriched = ordersDF.join(citiesDF, "city_code")
which Spark would execute as a shuffle join if broadcast threshold isn’t triggered automatically.
- Factory Animation: The animation shows orders flowing toward the join machine and city info boxes flowing from the other side. In an optimal (broadcast) scenario, the City Info boxes might first get replicated to multiple mini-machines (imagine the city info belt splitting to feed every instance of the join machine on each partition conveyor). This is shown by the City Info boxes going into a “duplicator” device and appearing alongside each worker robot that handles orders – a visual metaphor for broadcasting the small dataset to all executors, thus no global shuffle needed. The orders then combine with the matching city box at the machine and come out enriched. In a normal shuffle join scenario, the animation might instead show teleport tubes: orders by city code flying through tubes to meet city info by city code on the other side. This would look more chaotic, highlighting the extra step. The user will see the same final output (orders with city names) but the animation differentiates whether a broadcast happened (straight direct join flows) or a shuffle (lots of network tube activity).
- Judge Feedback: If the user used a broadcast join or similar strategy, the Run Report might be: - Output ✅ Correct (all orders have correct city names). - Shuffles: 0 (or “Low”) – because broadcast join avoided shuffling large orders dataset[1]. - Time: likely marked faster (since we assume broadcast is faster for this size ratio). - Perhaps a note: “Used broadcast join – efficient!” They would likely get 3★ for this optimal approach.
If the user did a normal join with no broadcast hint, the output is still ✅ correct (functionally no difference), but performance metrics would show: - Shuffles: 1 (or “High” – one big shuffle happened). - Time: slower (simulated). - The star rating might drop to 2★ because they missed the optimization. In that case, a hint would appear: “You joined a small and a large dataset without a broadcast. Spark had to shuffle the big dataset. Try broadcasting the small dataset to speed up the join.” This directly maps the game scenario to Spark advice, teaching why broadcast joins are beneficial (avoid network shuffle of big data).
Puzzle 3: “Total Factory Output” (Aggregation Puzzle, Easy/Medium)
- Scenario & Visual Setup: This puzzle’s factory has one main conveyor carrying a mix of products each with a type and a quantity (imagine each box has a label like product type and an integer count). At the end of the line, the boss wants to see the total quantity of products by type. Visually, there are multiple counting machines, one per product type, or one machine that can aggregate by switching mode. Initially, the products are unsummarized (just individual counts). The goal is to have an output display or bins that show, say, “Type A: 150 units, Type B: 300 units,” etc., combining all the small counts.
- Spark Concept: Aggregation (reduceByKey or groupBy + sum). The user needs to aggregate data by key. It’s a straightforward Spark task but illustrates combining data across partitions (which typically involves a shuffle to bring same keys together). It also can introduce the idea of combiner functions or partial aggregation (map-reduce concept) if we want to hint at efficiency (though that might be beyond MVP scope).
- Task for User: Given an RDD or DataFrame of (productType, quantity) records, produce an output of total quantity per productType. For example, input might be [("A", 10), ("B", 5), ("A", 20), ...] and output should be [("A", 150), ("B", 300), ...] after summing all. In PySpark:
totals = productsRDD.reduceByKey(lambda a, b: a + b)
or using DataFrame:
totals = productsDF.groupBy("type").sum("quantity")
either is acceptable.
- Correct Solution Sketch: As above, a one-liner reduceByKey is perfect. Some users might do groupByKey followed by sum in Python, which works but is less efficient (Spark would still shuffle but not combine on the map side). The judge might not differentiate that nuance in Phase 1, as both produce correct output but one has more data shuffle overhead. However, we could optionally reward reduceByKey as a slightly better approach (since it does partial aggregation before shuffle). This may be too granular for MVP, so likely any grouping+sum that yields correct results is fine.
- Factory Animation: The input conveyor feeds into a summing machine. The machine could be depicted with multiple counters (or worker robots each handling a particular product type if partitioned by type). As boxes flow in, the machine directs them by type: e.g. all “A” type boxes go down one chute inside the machine, where a counter adds up their quantities; “B” type boxes go to another chute, etc. Teleport tubes might appear if the machine has to gather same types from different input partitions – i.e., showing that initially items were on different belts internally and had to be rerouted by type (a visual metaphor for the shuffle in aggregation). At the end, the machine outputs one box or one label per product type with the total (like a big box labeled “A: 150”). The user sees that all those scattered numbers were combined into a few summary outputs.
- Judge Feedback: The correctness check verifies the sums for each product type. If correct, ✅ Output is good. Performance: an aggregation causes one shuffle by default to bring like keys together (Spark does a shuffle sort for groupBy unless optimized by combiners). So likely Shuffles: 1 is expected. The time might be moderate but acceptable. If the user used the ideal reduceByKey, we might simulate slightly less shuffle data volume (but Phase 1 might not simulate that in detail). We may not distinguish at MVP level and just consider any correct aggregation as 3★ since the puzzle’s point was to teach aggregation. If we do differentiate, maybe a subtle hint if someone uses a naive approach: “Using reduceByKey could be more efficient than groupByKey for summing values, as it combines data before the shuffle.” But this level of hint might be Phase 2 territory. For now, likely any correct sum gets full credit, and hints only if they did something incorrect (like forgot to sum at all). If incorrect, maybe they just didn’t aggregate, so output is wrong – hint could simply point them to use a grouping/aggregation function.
Puzzle 4: “Filter Before Merge” (Optimization Puzzle, Medium)
- Scenario & Visual Setup: This puzzle emphasizes doing filtering early to reduce data. The factory initially has a conveyor of mixed items, where some are defective (marked with a red X, for example) and others are good. Further down, there’s a join machine that merges this stream with another (maybe adding extra info to each item). The catch: the defective items should not be processed at all – they should be removed early. The goal described to the user: “Remove defective products before they reach the merge, to avoid jams.” The initial state shows defective items going into a machine they shouldn’t, causing a slowdown (maybe an animation of a machine clogged by useless items).
- Spark Concept: Filter pushdown / operation ordering. The puzzle wants the user to put a .filter() or where() before a join (or another heavy operation) rather than after. It teaches that filtering out unneeded data early will save work. This is a common Spark optimization: don’t join or shuffle data you’re going to drop anyway[4].
- Task for User: The starting code may be given partially, for example:
clean = itemsDF.join(infoDF, "key")  # join first
result = clean.filter(col("defective") == False)
which first joins everything then filters. The user’s job is to modify it to filter first:
clean = itemsDF.filter(col("defective") == False).join(infoDF, "key")
(assuming itemsDF has a boolean or flag for defective). Alternatively, if using RDD:
filtered = itemsRDD.filter(lambda item: not item.defective)
result = filtered.join(infoRDD)
The puzzle might explicitly mention: “We only want to process non-defective items. Make sure to remove defectives as soon as possible.”
- Correct Solution Sketch: As above, apply the filter before the join. The expected correct solution is a reordering of operations. If the user just runs it as given, it will produce correct final output (defectives removed) but inefficiently. So the puzzle is about recognizing the optimization rather than pure correctness (which adds an interesting twist: there’s a notion of a “better” vs “worse” correct solution). Possibly the puzzle could be set up so that if they join first, some performance threshold fails (maybe it “times out” or “overloads” in the story). For MVP simplicity, we may just accept both but the star rating depends on order.
- Factory Animation: The initial visual setup could show a lot of defective items (marked red) along with good items (green) all heading towards the join machine. If the user runs the unoptimized version (join then filter), the animation shows all items entering the join machine, causing it to handle unnecessary data – maybe the machine slows down or a warning icon appears. After the join, the defective items get tossed out by a filter machine (depicted as a later stage where red-marked boxes are removed and put in a trash bin). This late removal is visualized as costly because the join machine did wasted work.
If the user filters first, the animation changes: a filter machine (perhaps a robot arm that plucks out red X boxes) comes before the join machine. So only good (green) items reach the join. This time, the join machine processes fewer items and runs smoothly, and the output is the same except no defectives ever appear past the filter. The difference is subtle in output (output correctness is the same either way: only good items with info) but visually and in metrics, the early filter is better.
- Judge Feedback: Both approaches yield correct output (assuming defectives were meant to be removed). So correctness ✅ likely regardless of order (unless the puzzle explicitly fails the late filter as “inefficient solution not accepted” – but for learning, better to accept it but give low score). The performance metrics will starkly differ: - If filter-first (optimal): Possibly 1 stage for filter + join combined (Spark can often push filter past join or do it in the same stage if on one side, but anyway less data shuffled). Shuffles: maybe 1 (for join) but it transfers less data because defectives were dropped. Time: lower. Memory: lower. - If filter-last (suboptimal): Still 1 shuffle for the join, but more data went through it. We simulate a higher runtime. Possibly mark “Time: High” or “Processing wasted on 1000 defective items”. The star rating might be 3★ vs 1★ difference. The hint for a suboptimal run would explicitly say: “You filtered after the join. Try filtering out unnecessary items before joining to reduce the data processed[4].” This trains the user to think about operation order in Spark (a critical performance insight).
Puzzle 5: “Cache or Not to Cache” (Debug Puzzle, Hard)
- Scenario & Visual Setup: In this scenario, the factory is doing a multi-step process on a single dataset. For example, it reads a batch of items, then does two different transformations/outputs from it. Perhaps the factory has one conveyor of raw materials, and then splits into two different machines: one machine counts how many items of each type (like a report), and another machine filters and prepares items for shipping. The issue presented: the factory keeps slowing down on the second stage because it’s recalculating something. The hint in the problem text: “The factory is reading the same data twice for two different outputs – maybe we can store intermediate results.”
- Spark Concept: Caching/persisting an RDD/DataFrame to reuse it. If the code is doing expensive computation twice, caching once can save time. This puzzle is semi-advanced for Phase 1 and might be one of the later, hard puzzles. It introduces using .cache() and understanding when to use it.
- Task for User: The starter code might be:
data = loadData()  # assume this is an expensive read or transformation
result1 = data.filter(...).groupBy(...).count()   # first usage
result2 = data.map(...).filter(...).collect()     # second usage
The code is reading/processing data twice. The user’s task: add a .cache() after loading the data (or persist) to ensure the second usage doesn’t recompute from scratch. In DataFrame API, maybe they should do data = data.cache().
- Correct Solution Sketch:
data = loadData().cache()
result1 = ... # use data in first way
result2 = ... # use data in second way
Optionally, they might also unpersist at the end, but not needed for correctness. The main point is caching the shared input.
- Factory Animation: The initial run without cache would be shown as: the conveyor of raw materials goes through an expensive preprocessing machine to produce data. That machine is depicted as slow (maybe it’s complex, or reads from a warehouse). Then for result1, the items go through counting machine, etc. When it moves to result2, we see the same raw materials go through the expensive preprocessing machine all over again (maybe the animation rewinds or another batch goes through it) before the second transformation. This causes a delay – maybe a graphic of that machine heating up or a timer icon.
If the user caches the data, the animation changes after the first pass: we see the items get stored in a big buffer (like a storage unit or cache container) after the first pass. Then the second transformation pulls the data directly from that cache store instead of re-running the expensive process. Visual cues: a big “CACHE” box or warehouse that holds data in memory; second time, the conveyor diverts from cache to the next step, bypassing the expensive machine. The effect: the second operation starts faster.
- Judge Feedback: If not cached, the code still produces correct outputs, but the performance metrics show a problem: - Stages: possibly 2 sets of stages, indicating the source was read twice (Spark would show two jobs or two actions triggered a recomputation). - Time: definitely higher (almost double). - The system might simulate this by saying “Time: 10s – Slow (recomputed data twice)”. - Perhaps memory usage was low though since nothing was cached. And star rating might be 1★ or 2★ at most. The hint would be: “You processed the same data twice. Consider caching the data after the first use to speed up subsequent uses.” This nudges the user to use cache().
If cached properly, the metrics improve: - Time: maybe 5s – Good. - Stages: shows that after caching, second action did not repeat earlier stages (simulate as fewer total stages or an amber light turning green). - A note might say “Dataset cached – second step reused it from memory.” Star 3★ for implementing caching correctly.
This puzzle thus teaches when caching is beneficial, and also that caching has to be used carefully (but Phase 1 keeps it simple: caching is good if you reuse a dataset).
These five examples cover a range of Spark fundamentals: grouping/shuffling, join optimization, aggregation, filter pushdown, and caching. Each is wrapped in a fun narrative and visual context. For Phase 1 content, we would create around 15–25 puzzles in total, divided by difficulty and concept tags: - Difficulty could be labeled as Easy (introduction to concept, usually just one transformation), Medium (may involve two transformations or an optimization aspect), Hard (requires understanding of performance trade-offs or multiple steps). - Tags would include the key Spark topics: e.g. join, broadcast, shuffle, aggregation, skew, cache, partitioning, filter, transformation order. For instance, the above examples would be tagged as: Puzzle 1 (shuffle, groupBy), Puzzle 2 (join, broadcast), Puzzle 3 (aggregation, shuffle), Puzzle 4 (filter, optimization), Puzzle 5 (cache, persistence). - We would ensure multiple puzzles for popular tags: e.g. a few different join puzzles (one focusing on broadcast vs shuffle, another on different join types maybe), a couple on skew (maybe Phase 1 might touch skew lightly or leave it for Phase 2), and so on. This non-linear tag system means users can either follow a track (a guided path, e.g. “Basics track” for easy puzzles then “Advanced track”) or jump around focusing on specific weaknesses (the app could recommend “More join puzzles” if the user struggled with them).
Scoring & Feedback Model in Phase 1
The MVP includes a straightforward but informative scoring and feedback system, as glimpsed in the Run Report above. Here we outline how scoring works and what kind of feedback users receive for learning:
•	Correctness Checking: Each puzzle has a defined expected output (for given sample input data) or an expected transformation effect. The Judge backend will run the user’s code on the puzzle’s input dataset and compare the output to the expected output. This is similar to how LeetCode provides example test cases. For simplicity, Phase 1 puzzles use small hard-coded datasets where equality checks are easy. If the outputs match exactly (or for aggregations, order-insensitivity might be considered), the solution is correct. If not, it’s incorrect. The feedback on incorrect output might show a small example of discrepancy (like “Expected 10 items, got 8” or “The total for category A was wrong”). We ensure the user knows it’s a functional correctness issue, not just performance.
•	Performance Metrics: The judge will also compute or simulate metrics from the execution:
•	Execution Time: In Phase 1, rather than actual wall-clock time (which would be tiny for small data), we use a simulated cost model. For each transformation in the user code, we have an internal idea of how costly it would be on a big data scenario. For example, a shuffle operation might add a big time penalty in the simulation, a broadcast join would add a small overhead, a simple map is negligible, etc. We can present this as a relative time or a rating (fast/okay/slow). This way, even on small data, we’re teaching the relative cost of operations. As the user moves the slider toward better practices, the “time” in the report goes down.
•	Shuffles & Stages: We count how many wide transformations (shuffle-inducing) are in the plan. For DataFrame API, we could actually inspect the logical plan or simply pattern-match common ops. For RDD API, certain ops like groupByKey, join, repartition cause shuffle. This number is surfaced in the report. Additionally, the number of Spark stages is essentially number of shuffles + 1 (plus perhaps extra for caching boundaries, etc.). We can derive a rough stage count similarly. These metrics give users a sense of pipeline complexity.
•	Resource Utilization: We simulate whether the data was balanced across partitions or if one partition got much heavier (skew). For example, if a user groups by a key and the input data has one key that accounts for 50% of data, the judge (which knows the input distribution for the puzzle) can flag a skew. In Phase 1, this might be done in one of the harder puzzles explicitly about skew (e.g. a puzzle where data is heavily skewed to teach them about the issue). The report might say “Max partition had 5x the data of the average partition – Skewed” if that happens. If the user solved it in a way that alleviates skew (like salting keys or using a trick), the skew metric would improve.
•	Memory/Cache: If the user uses .cache(), we can note memory usage. Perhaps something like “Cached 1 dataset – used X MB memory (simulated)”. This is more to acknowledge they used caching.
•	Star Rating: After computing the above, a star (or medal) rating is assigned:
•	3 Stars (Optimal): Solution is correct and meets all efficiency criteria (no unnecessary shuffles, used recommended strategies like broadcast or filtering early, etc.). Essentially, the user solved it “the Spark way”. For easy puzzles, 3★ might simply mean they got it correct (since there might be only one obvious way). For optimization puzzles, 3★ requires the optimal approach.
•	2 Stars (Correct but Could Improve): Solution is correct but has some performance issues. Maybe they didn’t use broadcast or they left in an extra shuffle or didn’t cache when beneficial. The code works but a Spark expert would do better. Most intermediate solutions will fall here, which encourages iteration for that extra star.
•	1 Star (Correct but Poor Efficiency or Incorrect but Close): Perhaps used a very inefficient method that would not scale (like collecting data to driver and looping in Python, which we might simulate as extremely slow, or doing double work when not needed). Alternatively, if we consider partial credit, an incorrect solution that is on the right track might get 1★ just to encourage (though typically if incorrect we might not give stars at all). Phase 1 might keep it simple: stars only if output is correct, and among correct ones differentiate efficiency.
•	Hints & Explanations: As mentioned, if the user doesn’t get 3★, the system provides one primary hint about how to improve. Hints are triggered by rules:
•	e.g., If a join was used without broadcast and the small side is below a threshold, trigger the broadcast hint.
•	If .groupByKey().mapGroups() was used instead of reduceByKey, trigger a hint about combiners (maybe Phase 2).
•	If a filter is after a join, hint to push it before.
•	If a huge skew is detected, hint about skew solutions (like “One key is dominating the data – consider if you can repartition by a more granular key or handle the skew separately.”).
•	If they used cache unnecessarily (not in our examples, but say they cached but only used data once), hint “Caching wasn’t needed here – it only helps if you reuse data.” These hints are short (one sentence or two) so as not to give the full solution, but enough to make the user think.
•	Learning Resources: (Optional in MVP) We might provide a “Why?” link or expandable explanation after the user solves or sees a hint. Clicking it could give a bit more theory. For example, after the broadcast join puzzle, an explanation panel could briefly describe: “Broadcast joins avoid shuffling the large dataset by sending the small dataset to all workers[1]. This saves network and time in large-scale data.” This ties the user’s experience back to Spark knowledge, reinforcing learning.
The scoring and feedback in Phase 1 aim to balance positive reinforcement (gamified stars, celebrations for correct solutions) with constructive guidance (hints and metrics for improvement). Because it’s an MVP, the system will use a simplified model of performance (not a full Spark cluster execution, which is overkill for small puzzles). The key is that users start building an intuition: e.g. “oh, shuffles bad, broadcast good in certain cases” or “if I see a red light in animation, something’s inefficient.” This sets the stage for deeper challenges in later phases.
Tech Stack & Architecture (Phase 1 MVP)
To ship quickly and ensure the app runs in a browser with interactive graphics and code execution, we propose a React + FastAPI tech stack, along with supportive libraries:
•	Front-end: React will be used to build the user interface. React is ideal for managing UI state and dynamic components needed for the game (like starting/stopping animations, toggling views, showing reports). We can structure the front-end into components:
•	A Puzzle Selection screen,
•	The main Puzzle interface (with sub-components for Factory View animation canvas, Code Editor, Run Report modal, etc.),
•	Possibly a Navbar or Dashboard to show user progress (stars earned, etc.).
We will integrate the Monaco Editor in the React app for the code editing area, using a library like react-monaco-editor[5]. Monaco provides syntax highlighting and a familiar coding experience (since it’s the VS Code editor) which enhances the UX for writing code. We can configure it for PySpark syntax (Python highlighting, maybe some custom autocompletion for Spark commands if possible).
•	For the Factory View animation, we have a few options:
o	Use plain React + CSS/JS animations (e.g. using <div> elements to represent boxes and moving them with CSS transitions or a library like GSAP).
o	Use a canvas or WebGL approach for more complex animation. A library like D3.js (good for SVG-based animations), or PixiJS (for WebGL sprite animations), or even React’s own canvas drawing via a component. Since the graphics might involve moving multiple objects concurrently, a game framework or canvas might be smoother than DOM elements. We could start simple (CSS animations for moving elements on a grid) and evolve if needed.
o	The front-end will handle the timeline of the animation. We might predefine some animation sequences for each puzzle state (for example, if a shuffle occurs, animate tubes accordingly).
•	The React app will communicate with the backend via HTTP requests (or WebSockets if we want a live stream of events, but not necessary for MVP). On pressing “Run”, the front-end sends the user’s code to the backend API, then disables input and plays the animation. The animation might either be purely driven by the front-end (knowing roughly what the code will do from puzzle config) or coordinated with backend responses. Simpler approach: the backend returns a script of events or just the results+metrics, and the front-end decides how to animate based on what operations were detected.
•	Back-end: FastAPI (Python) will serve as the backend, providing API endpoints for the core functionalities:
•	Endpoint to execute/evaluate code for a puzzle (e.g. POST to /run with puzzle ID and code). FastAPI is a modern, high-performance Python web framework that will allow us to easily build these endpoints and handle requests quickly[6]. It has asynchronous support, which could be useful if we manage code execution with async tasks or need to handle multiple users concurrently.
•	Endpoint(s) to fetch puzzle data (e.g. GET /puzzle/{id} to get initial state, description, etc., though this could also be bundled in front-end or static files for MVP).
•	The backend judge logic can work in two possible ways for Phase 1:
a.	Simulation Mode: We do not run an actual Spark cluster. Instead, for each puzzle we have a predefined input (as a small list or pandas DataFrame) and an expected output. The backend can run the user’s PySpark-like code in a controlled local environment. For instance, we can use PySpark in local mode (Spark installed and master="local"), executing the code snippet with SparkSession. Given the small data, it should be fast. However, running arbitrary user code has risks (security, infinite loops). To mitigate, we could sandbox it (using timeouts, running in a container or separate process, or heavily sanitizing allowed operations). Alternatively, we can interpret the code: parse the user’s code (since puzzles are small, maybe they follow a pattern) and simulate what it would do – e.g., if user calls groupBy, our code recognizes that and knows a shuffle would happen, etc. This simulation approach might actually be easier for consistent metrics and avoiding actual Spark dependency in MVP. We could harness a simple Python sandbox or even use exec on a restricted globals with PySpark imported (risky but manageable with careful constraints).
b.	Actual Spark (local): Spin up a local Spark session and DataFrames for the small data, run the code, collect results. This ensures accuracy but brings Spark’s overhead. Given the tiny scale, it might be okay. We can configure Spark to use a small number of threads. FastAPI could call a worker function that executes the Spark job and captures metrics from the Spark UI or logs. This is more complex to implement in MVP, so leaning to simulate is wise.
•	The backend, after execution, computes the metrics and success criteria. If using simulation, we generate metrics via rules (as discussed earlier). If using real Spark, we can inspect the SparkPlan or listen to Spark events for shuffle count, etc. Spark’s explain or query plan might reveal number of stages and if broadcast was used (the physical plan often says “BroadcastHashJoin” vs “SortMergeJoin”). We can use that to drive metrics automatically, which is neat because it’s real. For example, if the plan contains BroadcastHashJoin, we know broadcast happened. Spark also has metrics for bytes shuffled, etc., but in local mode with tiny data that might all be zero or trivial – hence simulation or forcing some scaling factor would be needed.
•	FastAPI returns a response JSON with fields like {"correct": true, "metrics": {"time": 5.2, "stages": 2, "shuffles": 1, "skew": False}, "hint": "try broadcast", "outputPreview": [...]} etc. The front-end receives this and displays the Run Report accordingly.
•	Tech note: We might run the backend itself on Docker for easy deployment. FastAPI can be run with Uvicorn in a container. This aligns with potentially deploying on AWS (e.g. AWS Fargate or Elastic Beanstalk) or running locally for development via Docker-Compose. The user specifically mentioned AWS but also that local with Docker is fine – so our design uses standard open-source tech (React, FastAPI, Python, Spark) which can be containerized and deployed anywhere (AWS, Azure, on-prem, etc.).
•	Database/Storage: In Phase 1, we might not need a heavy database. Puzzle definitions can be stored in JSON or a small database since the content set is at most ~25 puzzles. User progress (accounts, solved puzzles, stars) might be stored if we have user login, but MVP could even store in local storage or a simple server session for a demo. If multi-user and persistent, we can use a lightweight database like SQLite or a hosted service. However, to keep MVP simple, we might even skip login and just let anyone play (progress can be ephemeral or stored in browser).
•	Communication: The front-end triggers a run via an HTTP POST to the FastAPI backend. For the animation synchronization: Because the code execution and animation are tied to the same events (transforms), we have two choices:
•	Simplified approach: The front-end knows what to animate based on the puzzle and perhaps by analyzing the user’s code string. For example, if the puzzle expects a groupBy, the front-end has an animation script for “group by these categories”. This requires the front-end to have some understanding of what the user did – which might be achieved via backend hints. Alternatively, the backend can return an ordered list of operations it detected (e.g. ["filter", "join(broadcast)", "groupBy"]) and then the front-end runs the corresponding animation sequence. This decouples execution from animation a bit, making it easier to ensure the animation matches the user’s code logic.
•	Advanced approach: Use WebSockets to stream events. E.g., if we actually run Spark, we instrument it to send messages like “starting shuffle” or “broadcast in use”. But that’s overkill for Phase 1 where puzzles are small and we can just animate after the fact. For MVP, returning a summary of what happened and then animating is fine.
•	Example Tech Flow (Run): User hits run -> React calls /run -> FastAPI runs judge -> response says correct=true, usedBroadcast=false, stages=2, shuffleCount=1 etc. The front-end then:
•	Plays the appropriate animation (maybe it sees shuffleCount=1 and it knows that during the join step to show teleport tubes).
•	After animation (or concurrently near the end), show the metrics and stars to the user.
•	Why React + FastAPI? React ensures a responsive, modular UI, and FastAPI is chosen for its high performance and ease of building REST APIs. FastAPI can handle multiple runs concurrently and is built on ASGI for efficiency (which means even if one user’s code is running, the server can still respond to others asynchronously)[6]. Both frameworks are well-documented and widely used, which helps developers quickly build the MVP. The choice is also aligned with keeping it open-source and easily containerizable (no heavy enterprise dependency). We also benefit from Python on backend since Spark (PySpark) is Python-friendly, and we can reuse Spark’s Python API directly if needed.
Data Model Sketch (for Puzzles & Progress)
Even in an MVP, it’s important to structure the data about puzzles, users, and results. Here’s a simple data model outline:
•	Puzzle Definition: Each puzzle can be represented as an object or table entry with fields:
•	id: Unique identifier (e.g. "puzzle_1_fruits").
•	title: Short name (e.g. "Group the Fruits").
•	description: The text description shown to the user (scenario and goal).
•	difficulty: e.g. Easy/Medium/Hard.
•	tags: list of concept tags (e.g. ["shuffle", "groupBy"]).
•	initial_data: The input dataset for the puzzle. This could be stored as a small JSON (for example, a list of records or a tiny CSV). For ease, we might store a Python snippet or a predefined Spark DataFrame construction. E.g. for fruits: a list [("apple",1),("banana",1), ...].
•	expected_output: The expected result dataset (in a similar format to initial_data). Or a function to verify output (for instance, some puzzles might accept outputs in any order, so we need a custom comparator).
•	solution_code: (Optional) A reference solution code snippet that achieves the goal optimally. This can be used by developers for testing and also to compare user solution for hints (e.g. we know what an optimal solution looks like).
•	metrics_solution: (Optional) Precomputed metrics for the optimal solution (to help rate user solutions).
•	animation_script: (Optional) Data about how to animate this puzzle – e.g., coordinates of belts and machines, what animations to trigger for certain operations. This can be quite complex, so it might be defined in code rather than data. But we could have a structured representation of the factory layout: positions of belts, machines, mapping of data partitions to those belts, etc. This enables the front-end to render the puzzle’s factory view.
•	User Data: (If we have user accounts/profiles in MVP)
•	user_id, username, etc.
•	completed_puzzles: list of puzzle IDs the user solved.
•	stars_per_puzzle: mapping puzzle ID -> stars achieved.
•	attempts: could store history of attempts for analytics (not necessary for MVP, but useful to see common wrong answers).
•	If no login in MVP, we might just keep this in memory or local storage. If login exists, then a user table and a progress table in a database would be needed.
•	Attempt / Run Result: Each time a user runs code:
•	We might not store every run in a DB, but we can if needed (especially if wanting to show improvement or analytics). For MVP, probably not storing all attempts server-side to keep it simple. But we do have the data on the client to show the last run’s results immediately.
•	If storing, an attempt record could have: user_id, puzzle_id, code_submitted, was_correct, stars_awarded, timestamp, metrics (json). This could help if we want to resume a session or show how many tries they took.
•	Non-linear Curriculum Structure: To support tracks and recommendations:
•	We might have a separate structure for Tracks (e.g. track id, name, sequence of puzzle IDs). For MVP, we might not implement multiple tracks fully, but we can tag puzzles by track (like "Game Basics", "Interview Prep mini", etc.).
•	For Tags, puzzles already have tags. We could have a dictionary of tag metadata (each tag with a description, and maybe which puzzles correspond). This can drive a recommendation engine later (“user struggling with tag X – find other puzzles with tag X”).
•	In Phase 1 MVP, this might be simply informational (we label puzzles with tags and difficulties for manual selection by the user). A recommendation system might be a stretch goal beyond MVP.
•	Configuration & Deployment: We keep the application stateless where possible. The puzzles and any needed static data could be bundled with the backend or served as JSON files. Because the user mentioned Docker and AWS:
•	We’ll set up Dockerfiles for both the React app and FastAPI app for consistent deployment. Possibly use Docker Compose to run them together.
•	The FastAPI container could include Spark or the logic for simulation. If Spark is used, the image might be bigger (Spark + Java dependencies). Alternatively, we simulate in pure Python which keeps it slim.
•	This architecture (React front, FastAPI back) is cloud-friendly – we could host the backend on AWS (EC2 or Fargate) and front-end on S3 + CloudFront as a static site or similar. But that’s deployment details; the key is MVP runs locally via Docker for easy development.
In conclusion, Phase 1’s design centers on creating a fun, educational environment for Spark beginners to solve self-contained puzzles. The technical choices (React, FastAPI, possibly PySpark for execution) are made to ensure we can build and iterate quickly. The data model and structure are kept simple (small puzzle set, no heavy user management at first) so we can focus on delivering the core interactive learning experience. This sets a solid foundation to expand the product in Phase 2 and 3 with more complex scenarios.
