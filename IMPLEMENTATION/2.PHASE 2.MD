## Phase 2 – Pipeline Mode / Optimization Challenges

Phase 2 expands the scope from bite-sized puzzles to more realistic, multi-step Spark jobs. The idea is to simulate real-world pipelines where the challenge isn’t just writing a correct transformation, but optimizing a sequence of transformations to meet performance goals. The game evolves beyond isolated factory gadgets to a full production line with multiple stages.
Concept & User Flow for Phase 2
•	Introduction of Pipelines: In this mode, a “puzzle” is now a complete Spark job or pipeline, composed of several steps (e.g., reading data, joins, aggregations, writes). The Factory View will show a bigger factory floor with multiple machines connected in series or parallel, reflecting the DAG (Directed Acyclic Graph) of Spark operations for that job. For example, one pipeline might involve: read data -> filter -> join with another data source -> aggregate -> write result. Each of these could be a machine or section in the factory.
•	User’s Goal: The user is given a working pipeline (it produces correct results as given) but with suboptimal performance. There is a target goal such as “Make the job run under 1 hour” or “Reduce cost by 30%” or simply “Optimize this pipeline’s performance (3★ = excellent performance)”. It’s akin to refactoring or tuning an existing solution, which is a common scenario in real life (you rarely write a perfect Spark job upfront; you iterate to optimize).
•	Viewing the Pipeline (Factory & Stats): When the user opens a pipeline challenge, they see:
•	Factory Pipeline View: A zoomed-out view of a factory line with multiple connected stages. Each stage might have its own conveyors and machines, and between stages you can see conveyors linking them (which correspond to RDD/DataFrame lineage). Key points like shuffle boundaries might be indicated (e.g. a teleport tube connecting two stage machines, labeled Stage 1 -> Stage 2). If one stage’s output is particularly large or skewed, the visualization might highlight that (e.g. a huge pile of boxes on one conveyor vs others).
•	Perhaps an initial metric summary (like a Spark job overview): e.g. “Initial job: 5 stages, 3 shuffles, processed 100M records, took 2 hours, spilled to disk”. This gives the user a clear understanding of what’s wrong.
•	The code for the pipeline, possibly in a larger editor that spans multiple steps or a notebook-like format. The user might see the code in one place (it could be a longer PySpark script), or we might break it down into sections for each stage for clarity. For MVP of Phase 2, a single code editor with a multi-step Spark job script is fine.
•	User Action – Optimize Code: The user will modify the Spark code to improve it. This could involve:
•	Adding hints like .hint("broadcast") or using the broadcast function on joins.
•	Reordering operations (e.g. move a heavy filter up earlier, or changing join order).
•	Adding a cache() on an often-used intermediate DataFrame.
•	Changing the partition counts (e.g. use .repartition(n) or adjust spark.sql.shuffle.partitions).
•	Using different Spark transformations that are more efficient (for example, replacing a groupBy followed by filter with a more direct use of aggregations, etc.). Essentially, the user is free to rewrite parts of the pipeline, as long as the final output remains correct. We will likely provide the initial code and allow them to edit it – this is an open-ended challenge more than filling in blanks.
•	Running & Comparison: The user runs the pipeline. Because these are more complex, the Run Report now compares Before vs After:
•	We present the original stats versus the user’s new stats side by side. For example:
o	Original runtime: 120 min, User’s runtime: 45 min.
o	Original shuffle data: 500 GB, Now: 100 GB.
o	Original stages: 5, Now: 4.
o	Original largest partition: 60% of data in one partition, Now: 20% (improved skew).
•	The output correctness is still paramount; if their changes break the output (i.e., result differs), that’s a failure even if it’s faster. So correctness must be preserved (like regression tests in optimization).
•	Visualization might replay the pipeline animation highlighting differences. For instance, if they removed a shuffle by broadcasting, the second run animation for that join stage will show no teleport tubes where before there were many. We could even do a ghost overlay of “before” vs “after” (e.g. faded red arrows showing old heavy data flow and green arrows showing new lighter flow).
•	Feedback & Scoring: As in Phase 1, they get stars or a rating, but here it’s specifically tied to improvements:
•	3★ if they meet or exceed the target improvement (or some threshold like >50% speed-up and handled key issues).
•	2★ if moderate improvement or partially solved issues.
•	1★ if minimal improvement or output only correct with no perf gain.
•	Hints would focus on what still can be improved. E.g. “The job is still bottlenecked by a skewed key, consider a strategy to handle skew (like salting).” Or “Stage 3 is still very slow – did you consider caching the data before Stage 3 to reuse it?”
Sample Optimization Challenges (Phase 2 Examples)
We will create a small set (around 5–10) of pipeline challenges, each based on common Spark performance scenarios. Here are a few example scenarios:
1.	Challenge 1: “The Daily ETL – Missing the SLA”
2.	Scenario: A pipeline reads logs (100 million rows) from storage, joins with a user info dataset, filters some events, aggregates to compute daily active users, and writes out results. The current implementation is too slow, missing the nightly SLA (takes, say, 3 hours instead of 1).
3.	Issues Present: Possibly the join is done without broadcast (user info is small), and a filter on logs happens after the join (meaning unnecessary data was joined). Also, the aggregation might be using groupByKey causing shuffle issues.
4.	Concepts Tested: Broadcast join, filter pushdown, using efficient aggregation.
5.	User’s Task: Modify the code to broadcast the small dataset and move the filter earlier. Maybe use countDistinct appropriately or avoid groupByKey.
6.	Expected Outcome: Fewer shuffles (one join shuffle removed), less data processed (filter early reduces data by 50% before join), overall stages maybe the same count but each stage lighter. Possibly caching if the same logs are used twice (if scenario had multiple outputs).
7.	Challenge 2: “Skewed Sales Report”
8.	Scenario: A pipeline processes sales data grouped by product ID to calculate totals and top sellers. One product (or a few) are extremely popular, causing one partition to handle 50% of data, leading to a slow aggregation stage and even spilling to disk.
9.	Issues Present: Data skew on aggregation key. As a result, one task is very slow (or fails).
10.	Concepts Tested: Skew handling techniques. (Spark has features like salting keys manually, or using DataFrame API’s approxQuantile and splitting, or even Spark’s built-in skew join mitigation with AQE[7], but in Phase 2 we might expect the user to do something manually since it’s educational.)
11.	User’s Task: Implement a solution to mitigate skew. For example, they could add a random salt to the key for aggregation and then later merge results for that key, or use a custom partitioner that spreads out the large key’s data across more partitions.
12.	Expected Outcome: The aggregation stage is now balanced. The metrics should show the max partition size came down drastically. Maybe stages increased by one because of the extra step (salt and unsalt), which is fine if performance is better. This challenge teaches that sometimes a more complex solution (additional stage) is needed to handle skew for overall speedup.
13.	Challenge 3: “Caching for Reuse”
14.	Scenario: A pipeline does several operations on the same base dataset. For instance, after initial cleaning, it computes two different reports (like in Phase 1’s cache puzzle but on bigger scale). In the original code, the cleaning transformation is done twice (once per report).
15.	Issues Present: Recomputing expensive steps multiple times, no caching. Possibly also the default spark.sql.shuffle.partitions is high causing overhead for small dataset later, etc.
16.	Concepts Tested: Caching and partition tuning.
17.	User’s Task: Persist the common cleaned DataFrame so it’s not redone, and perhaps coalesce or repartition it optimally for the next steps (for example, if after cleaning the dataset is small, reduce the partition count to avoid overhead in final actions).
18.	Expected Outcome: The job’s second half runs faster because it reads from cache. The metrics show reduced total CPU time and maybe one less stage (Spark would show cached result reuse as skipping a stage). If they also adjust partitions, tasks might reduce and scheduler overhead drops.
19.	Challenge 4: “Join Order Matters”
20.	Scenario: A pipeline joins multiple datasets: e.g., three tables A, B, C. The original code joins A with B (both large) first, then joins result with C (small). This is inefficient – maybe joining A with C first (small with large) then that with B would be faster, or using broadcasts for C.
21.	Issues Present: Suboptimal join order leading to a massive intermediate data shuffle.
22.	Concepts: Join order optimization, thinking like Catalyst optimizer (but here user does it manually).
23.	Task: Change the join sequence, or use .join(..., hint="broadcast") on C, etc. Possibly also partition the data on join keys beforehand.
24.	Outcome: The pipeline now has a smaller intermediate result and thus the second join is less expensive. Metrics show lower shuffle bytes and maybe one stage was combined or something.
25.	Challenge 5: “Too Many Tiny Files” (if we include file I/O aspects)
26.	Scenario: A job writes output to 1000 tiny files because default partition count was high, causing overhead in downstream processing. Or conversely, a job reading many small files causing too many tasks.
27.	Issue: Partition tuning problem.
28.	Concepts: Coalesce and Repartition, partition sizing.
29.	Task: Adjust the number of partitions for output or input to optimize (like use coalesce(10) before writing to reduce number of output files, or use repartition to distribute data more evenly for a stage).
30.	Outcome: Fewer output files (if writing), or fewer tasks if reading many small files combined. The performance improves (less overhead). The user learns to be mindful of partition counts beyond just functional logic.
Each of these challenges comes with a narrative (to keep the game theme, we’d frame them as factory issues: e.g., “The packaging stage is overwhelmed because one product’s orders are huge – fix it,” or “We have duplicate work happening on two lines – can you streamline it?”). The difference from Phase 1 is the complexity: multiple issues might exist in one pipeline, and the user has to find and fix as many as possible. It’s more open-ended and creative.
Judge View – Comparing Before & After
The judging in Phase 2 needs to emphasize improvement. Some features of the Judge View for pipeline mode:
•	Baseline Stats: For each challenge, we store the baseline performance (from the unoptimized code). These stats are shown as a reference. For example: “Baseline: 3 stages, 2 shuffles, runtime ~ 10 minutes, 1 out of 200 tasks straggling due to skew, output 20 files” etc.
•	User Stats: After the user runs their modified pipeline, we capture the same metrics and display them. This side-by-side comparison concretely shows what changed.
•	Correctness Validation: We still run the user’s code on a test input (it could be a scaled-down sample of the big data, or the logic to verify correctness of results through checksums, etc.). The output needs to match the original pipeline’s output (or at least be logically equivalent). If the user accidentally changed the logic (like filtering out some data unintentionally while optimizing), that’s a failure – the app will show that the output is wrong. This ensures they optimize without altering functionality, which is a valuable skill (don’t break the answer while making it faster).
•	Detailed Metrics / Spark Plan Info: We might present more advanced info in Phase 2’s report for those interested:
•	For example, list each stage with what operation it did and how long or how much data. Possibly even show a miniature Spark DAG or critical path.
•	If the user used broadcast join, mention in report: “Join between Orders and Cities used BroadcastHashJoin (small table broadcasted)[1].”
•	If they fixed skew, mention “Skew handled: largest partition size reduced from X to Y.”
•	This essentially educates on how those changes reflect in Spark’s execution. We can derive some of this if we use a real Spark backend by analyzing the query plan or execution metrics.
•	Scoring Algorithm: Phase 2 scoring might weigh multiple factors. For instance, we could assign a score out of 100 where:
•	50% is meeting the target runtime improvement (or a scaled measure of speedup),
•	30% is addressing specific known issues (did they use broadcast where applicable, did they handle skew, etc.),
•	20% is code quality (if we choose to enforce that, e.g., they didn’t do something hacky like using a non-distributed workaround that wouldn’t scale). But for user simplicity, we convert that to stars or a grade. Possibly just stick to stars like Phase 1, but accompanied by the comparison stats which are more informative.
•	Encouraging Multiple Solutions: In optimization problems, there may be more than one way to improve. The Judge could acknowledge this. For example, if a user achieved the goal by method A vs method B, both are valid. The hints system could be dynamic: if the user improved speed but not in the intended way, the app might still hint at the missed optimization. E.g., “Great, the job is faster now (you got it under 1 hour)! You achieved it by caching, which works. Another improvement could be broadcasting the small table to cut down one shuffle.” This way, even if solved, the user learns additional tips.
AI Assistance in Phase 2
While not fully implemented in MVP, we envision integrating AI to help users analyze and improve their pipelines. Some design ideas:
•	Automated Analysis: When a user runs a pipeline and it’s not optimal, an AI agent (maybe powered by an LLM or rule-based expert system) could analyze the Spark plan and metrics. It can generate a human-readable analysis of “What’s slowing down the job?”. For example: “Stage 2 (joining orders with cities) is taking 70% of the time. The join is using a sort-merge join, meaning both datasets were shuffled. Since the cities dataset is small (1000 records) and orders is large (10 million), broadcasting cities would avoid that shuffle. Also, I see that you filter orders by region after the join – filtering before would reduce data early.” This is essentially doing what a good Spark developer does when looking at the Spark UI and code.
•	Hint Generation: We already have static hints, but an AI could handle more complex patterns, or combine multiple hints into a prioritized suggestion list. The AI could also answer “Why” if the user asks for explanation of a suggestion.
•	What-If Suggestions: AI could propose alternative strategies: “Alternatively, you could have split the big groupBy into two steps to avoid skew. This trades off one more stage for better parallelism.” This helps users understand there might be multiple valid optimizations and the trade-offs involved.
•	Guided Optimization Mode: Perhaps an interactive chatbot assistant in the app for Phase 2 where a user can ask, “Why is this stage slow?” or “How can I improve further?” and the AI, having context of the pipeline, can explain or give hints. This would make the learning experience very rich, turning the game into a tutor as well.
•	Validation of Approach: If a user comes up with an unusual optimization, the AI could comment on it. For instance, if they choose to drastically reduce spark.sql.shuffle.partitions, the AI might warn “Be careful: lowering partitions too much can cause giant tasks. In this case, it seems fine.” or conversely “You dropped partitions to 1 – that avoids shuffles but now one task does all the work, which could be a bottleneck. Try a moderate number like 10.” This kind of nuanced feedback is hard-coded by rules but natural for an AI that understands context.
The AI integration should be designed to augment the user’s learning, not just give away answers. It should encourage the user to think about why a change helps. Likely in Phase 2, we’ll prototype a simplistic version (maybe a button “Analyze my job” that calls an API with a prompt to an LLM describing the plan and metrics, returning advice).
In summary, Phase 2 transforms the game into an optimization sandbox, closer to real Spark job tuning. It introduces complexity in both the code (multi-step pipelines) and the evaluation (comparing improvements). The Factory metaphor scales up: the user now manages an entire factory assembly line, not just a single machine puzzle. By tackling these, users gear up for addressing complex Spark issues, bridging nicely into Phase 3 where they’ll face free-form interview-style questions.
